Reviewer: fresh subagent; did not open `legacy/`; did not read the original's source. Date 2026-09-20.

Headline. On conversion CONTENT I found ZERO byte differences in about 122,000 compared executions (argv, JSON and TOON grammar,
numbers in both directions with the switch off and on, quoting, folding, expansion, blank lines, stats, error texts, the JS lane, 8 threads).
The hashed carriers are correct under collisions, duplicates and every key shape I could build. What is wrong is, again, outside what the
harness can see, and one of them is serious: **the port never reads file descriptor 0. It re-opens the path `/dev/stdin`
(`port/main.bend:83`)**, which gives wrong output with exit 0 for a seeked stdin, and a hard failure when stdin is a socket, which is what
Node.js `child_process` hands every child. The round-6 quadratic is fixed for ordinary keys, but two quadratic shapes remain in the new
carriers (keys that collide in the 16 hash bits; repeated keys in one JSON object).

## 1. Findings

Severity: HIGH = wrong bytes or exit code on plausible input; MEDIUM = contrived input, unregistered platform/resource difference, or superlinear time; LOW = documentation / DISC inaccuracy.
R7-1, R7-2, R7-3 (and the wrong explanation in R7-8) share ONE root cause: `File.open("/dev/stdin", "r")` instead of reading fd 0.
`strace` of the port: `openat(AT_FDCWD, "/dev/stdin", O_RDONLY) = 5` then `read(5, …, 1048576)`; fd 0 is never read (`review_R7/strace_port_stdin.txt`).
None of this is in DISCREPANCIES.md. DISC-006's own "Why" rejects re-opening fd 1 by path because it "fails where the original succeeds
(a socket, a descriptor inherited across a privilege change), which is a worse divergence" — stdin is read exactly that way. The native
binary, the launcher and the JS lane all behave the same. The corpus cannot see it: the harness always supplies a regular file at offset 0.
